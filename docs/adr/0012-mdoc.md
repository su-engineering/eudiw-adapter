# ADR-012: ISO mdoc (`mso_mdoc`) verification

Status: accepted. Implemented: issuer data authentication, mdoc authentication by device signature, the DeviceResponse rules, the OpenID4VP session transcript, DCQL `mso_mdoc` (with the age attestation rule), request metadata and the service integration. MSO revocation by Token Status List reference is implemented; other mechanisms of the second edition are pending.

## Context

OpenID4VP 1.0 Appendix B.2 carries ISO mdocs as `mso_mdoc`: the `vp_token` holds a base64url DeviceResponse, the DCQL credential query names a `doctype_value`, and the session transcript uses the `OpenID4VPHandover` structure (B.2.6.1) instead of device engagement. HAIP 1.0 section 5.3.1 adds that every mdoc comes in its own DeviceResponse and that ES256 and SHA-256 are the minimum.

The data structures and checks come from ISO/IEC 18013-5:2021 (first edition):
- clause 8.1 (CBOR encoding rules, and that cryptographic operations use the tagged byte strings exactly as received),
- 8.3.2.1.2.2 (DeviceResponse, Document, IssuerSigned, DeviceSigned),
- 9.1.2 (the mobile security object, MSO, and its signature),
- 9.1.3 (mdoc authentication),
- 9.3.1 and 9.3.3 (the reader's inspection and certificate validation procedures),
- Annex B (certificate profiles).

The ISO text is copyrighted and is not reproduced here or anywhere in this repository: code and documents cite clause numbers and describe requirements in our own words. The ISO examples are not used as test vectors. The standard may be read, but its terms of access forbid copying, storing or giving it to AI tools; implementing it needs no permission.

## Decision

1. **CBOR and COSE are implemented in core, with a test-scope cross-check.**
   - The decoder is small and strict:
     - definite lengths only;
     - no duplicate map keys;
     - valid UTF-8 text;
     - bounded depth, item count and input size;
     - no trailing bytes.
   - Every decoded item keeps its exact encoded bytes. Digests and signatures are computed over the bytes as received (clause 8.1), never over a re-encoding. Encoding is needed only for structures the verifier builds itself (the session transcript and the device authentication structure), which contain no maps, so their encoding is deterministic.
   - COSE_Sign1 verification builds the `Sig_structure` (RFC 9052 section 4.4) and verifies with the JDK.
   - Authlete's `com.authlete:cbor` (Apache-2.0) is used **in test scope only**: it decodes the same inputs for a differential check and signs COSE structures our code did not produce. This mirrors the SD-JWT decision in [ADR-005](0005-jose-and-sd-jwt-libraries.md).
2. **The algorithm comes from the key, never from the header alone.** Accepted algorithms:
   - ES256 (-7) or ESP256 (-9) with P-256;
   - ES384 (-35) or ESP384 (-51) with P-384;
   - ES512 (-36) or ESP512 (-52) with P-521;
   - EdDSA (-8) or Ed25519 (-19) with Ed25519;
   - EdDSA (-8) or Ed448 (-53) with Ed448.

   The protected header must name one of these and must match the key's curve.
3. **Brainpool curves are opt-in, in a separate module.** Clause 9.1.5.2 lets issuer and device signatures use brainpoolP256r1, P320r1, P384r1 and P512r1 (COSE curves 256 to 259). The JDK knows their parameters but cannot verify signatures on them, so `adapter-crypto-brainpool` brings BouncyCastle. Nothing changes until it is enabled (`BrainpoolSupport.enable()`, or `EUDIW_CRYPTO_BRAINPOOL=true` in the service, whose image carries the module); until then a brainpool key is rejected with `unsupported_algorithm`.
   - BouncyCastle is added as the last JCA provider and used explicitly, only where a brainpool key is involved: COSE signatures, certificate path validation (`PKIXParameters.setSigProvider` when a certificate or anchor of the path is on a brainpool curve) and CRL signatures. Everything the JDK verifies today keeps the JDK's providers.
   - ES256 allows brainpoolP256r1, ES384 brainpoolP320r1 and P384r1 (SHA-384), ES512 brainpoolP512r1. The fully specified ESB256, ESB320, ESB384 and ESB512 (RFC 9864, -265 to -268) name one curve each and are advertised only when enabled. ESP256, ESP384 and ESP512 stay NIST-only.
   - Curves are identified by their full domain parameters, never by key size, since brainpoolP256r1 and P384r1 share sizes with P-256 and P-384.
   - The test fixture is an mDL on brainpoolP256r1 whose certificates and signatures were made by OpenSSL, so BouncyCastle only verifies.
4. **Certificate validation reuses the existing path validation** (RFC 5280, trust anchors from configuration or ETSI trusted lists, CRLs). The IACA-specific checks of clause 9.3.3 and Annex B apply when the anchor is an IACA:
   - the country must match between the anchor and the document signer;
   - a state or province in the anchor must be repeated, identically, in the document signer;
   - the document signer certificate must carry the mDL document signer extended key usage and the digitalSignature key usage;
   - a returned `issuing_country` must equal the document signer's country, and a returned `issuing_jurisdiction` its state or province when it names one (clause 7.2).

   The Annex B profile also sets a maximum document signer validity (457 days) and makes a CRL distribution point mandatory. Those are issuer obligations. The reader does not reject for them; it records a conformance warning (`mdoc_signer_validity_over_457_days`, `mdoc_signer_without_crl_distribution_point`). CRLs are checked when the policy enables them, whatever the certificate's lifetime.

   A root certificate in the x5chain, which clause 9.1.2.4 says should not be there, is dropped before path validation, with the warning `mdoc_x5chain_includes_root`. It is never trusted: the path must still validate to a configured anchor or trusted-list certificate.

   They are applied to the `org.iso.18013.5.1.mDL` doctype by default. Other doctypes, such as the EU PID, are anchored by ETSI trusted lists whose own rules decide the certificate profile, so the mDL profile is opt-in for them.
5. **mdoc authentication uses `deviceSignature` only.** This is a profile restriction, not a reading of the base standard: clause 9.1.3 asks a reader to support both a device signature and a device MAC. The MAC key is derived by ECDH between the device key and the reader's ephemeral key (clause 9.1.3.5), and the OpenID4VP session transcript carries no reader key, so a MAC cannot be checked in this flow. A `deviceMac` is rejected with `holder_binding_invalid`.

   The device signature (clauses 9.1.3.4 and 9.1.3.6):
   - is a COSE_Sign1 with a detached payload and an empty external AAD, its algorithm in the protected header and matching the device key's curve as in item 2;
   - is verified with the `deviceKey` of the issuer-verified MSO, never a key from the presentation;
   - covers the embedded CBOR of `["DeviceAuthentication", SessionTranscript, DocType, DeviceNameSpacesBytes]`, rebuilt by the verifier from this request's transcript and the `nameSpaces` bytes exactly as received.

   `deviceSigned` and its `nameSpaces` are mandatory. Every device-signed element must be covered by the MSO's key authorizations (a whole namespace or a listed element); without authorizations, none may appear. Device keys are accepted on the curves of item 2. The standard is not consistent here: it allows P-384 for issuer signatures, but its device-key curve table (Table 22) does not list it. A P-384 device key is therefore accepted with the warning `mdoc_device_key_curve_not_in_table_22`, and a policy with `mdoc_strict_conformance: true` refuses it with `unsupported_key`.
6. **The DeviceResponse is checked before its documents.** `version` (major version 1) and `status` are mandatory; any non-zero status rejects the presentation with `unprocessable_presentation`. `documentErrors` and per-document `errors` name what the wallet did not return and are left to DCQL. HAIP's one document per DeviceResponse is enforced; the base standard allows several.
7. **Age attestations answer nearby requests** (clause 7.2.5). A wallet asked for `age_over_NN` may return the nearest attestation it holds: `age_over_MM: true` with MM at least NN satisfies the request, and `age_over_MM: false` with MM below NN answers it with false. The value is reported under the requested element. Attestations that contradict each other (`age_over_A: true` next to `age_over_B: false` with A at least B) answer nothing, even when the requested element itself is disclosed, and the rule applies to `mso_mdoc` only.
8. **MSO revocation uses the IETF Token Status List.** The MSO's `status` carries `status_list` with an `idx` and a `uri`, the Referenced Token structure of the Token Status List (draft-ietf-oauth-status-list-21, section 6.3). It is checked exactly like an SD-JWT VC's: the list is fetched (CWT preferred, JWT accepted), its signer chain must validate to the policy's status anchors, `sub` must equal the `uri`, and `status_policy` decides what an unavailable list means. The second edition of ISO/IEC 18013-5 is expected to use this mechanism; if it defines something else, that will be added. An MSO `status` with any other mechanism has unknown status: rejected under `require_valid`, accepted under `reject_known_invalid`.

   The CWT form (section 5.2) is a COSE_Sign1_Tagged with protected `type` `application/statuslist+cwt` and the signer chain in `x5chain`; claims `sub` (2), `iat` (6), `exp` (4), `ttl` (65534) and `status_list` (65533) with `bits` and a zlib-compressed `lst` byte string.
9. **Tolerated departures are recorded, not hidden.** A credential that verifies despite one of the departures above carries a structured conformance warning. The service writes each one to the audit trail as a `conformance_warning` event with its code (and the `eudiw.events` metric), with no claims.
10. **An mdoc issuer is named by its trust anchor.** An mdoc carries no issuer identifier like `iss`. `allowed_issuers` and the result's `credential_evidence` use the subject name of the anchor the chain validated to, and `allowed_issuers` also matches the names of the trusted-list entities that publish that anchor. The document signer's own name is not used: it changes when the signer rotates, and any anchor can issue a certificate carrying another issuer's name.
11. **Claims are addressed by `[namespace, element identifier]`**, as in OpenID4VP DCQL for `mso_mdoc`. Only issuer-signed elements are returned. Device-signed elements are verified but never returned as claims.

## Consequences

- Fixtures:
  - eudi-dev v3.8.0 issues `mso_mdoc` credentials with a synthetic issuer key, and their output is committed as fixtures;
  - the OpenID4VP 1.0 Appendix B.2.6 examples are used as fixed vectors for the session transcript;
  - the Compose demo has the eudi-dev wallet present an mdoc PID end to end, and present one signed over the ISO/IEC 18013-7 transcript, which must be rejected; CI runs both;
- `deviceMac` is listed as unsupported in the feature matrix. Brainpool needs the opt-in module.
